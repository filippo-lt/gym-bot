## Facts found while reading the code
1. Token caps sum `input_tokens + output_tokens` only; `cache_read_tokens` and `cache_write_tokens` are stored in usage_logs but not counted.
2. The cap is checked before every model call in the loop (6 turns, 40 s wall clock; each request 35 s timeout, SDK maxRetries 2). Vision checks the same token cap before its call and records usage after. STT checks its seconds cap before downloading and records seconds after a successful transcription.
3. Cap replies are "AI budget reached. Commands still work." and "Voice budget reached. Text still works." They don't say which cap (day/month) or when it resets. There is no command showing usage.
4. Function maxDuration is 90 s; the processor stops claiming new inbox rows 45 s after the invocation started. Worst case per row: voice ≈ 15 s download + 20 s STT + 40 s AI loop; photo ≈ 15 s download + 40 s vision; text ≈ 40 s loop. A voice note or photo claimed late in an invocation can be killed at 90 s, then retried after the 150 s lease; three kills mark it failed.
5. Text: any AI error → "Sorry, I couldn't process that. Please try again." Voice: download and STT failures share one message. Photo: download, vision and "file too large" share one message. Errors thrown out of a handler (e.g. DB) give silence until the third inbox attempt, then "couldn't process your last message after 3 tries" with no reason. grammY wraps handler errors in BotError, so inbox.error mostly says "BotError". Drizzle wraps DB errors in DrizzleQueryError whose message includes SQL and params.
6. JobContext.send sends text only. There is one job (Thursday class question). M8 will add a morning job to the same JOBS array.
7. No backup or restore code exists. Tables use serial/bigserial ids, timestamptz, jsonb, text[], pg enums.

## Questions (answer each with your choice and a one-line reason grounded in SPEC/code)

### A. Backup format and delivery
A1. Which tables go in the backup? (a) every table in the schema, including runtime ones (inbox, chat_lease, job_runs, write_ledger, pending_actions, conversation_messages, usage_logs); (b) only domain/history tables; (c) every table, with an explicit exclusion list.
A2. How is "table-generic" achieved? (a) iterate the Drizzle schema exports (`getTableConfig`); (b) list tables from the database catalog (`information_schema`); (c) a hand-maintained list plus a test.
A3. How are rows serialised for lossless restore? (a) Postgres-side JSON (`to_jsonb` on read, `jsonb_populate_recordset` on write); (b) Drizzle `select()` objects serialised in JS with per-type mapping; (c) `pg_dump`-style SQL text.
A4. CSV shape: (a) one CSV per table inside a zip; (b) one CSV per table as separate Telegram documents; (c) a few key tables only as CSV (logs), JSON holds everything; (d) no CSV.
A5. Size handling: Telegram bot documents max 50 MB. (a) ignore for now; (b) gzip above a threshold; (c) refuse with a clear message above a threshold.
A6. Sunday job window and behaviour: what window after 18:00 Rome, and what happens when building/sending fails (silent retry, message the user, both)?
A7. What goes in the Sunday message besides the files? (a) nothing; (b) row counts; (c) row counts + the week's AI/voice usage; (d) a weekly training summary (SPEC §3 says "summary + backup").
A8. How should the coverage requirement ("a test fails if a schema table is missing from the export") be tested?

### B. Restore
B1. Target database: (a) only a fresh, empty, migrated database (local or a new Supabase project); (b) also into an existing database, merging; (c) into an existing database, replacing everything.
B2. How does the script pick the target? (a) `DATABASE_URL`; (b) a dedicated env var with no fallback (like `MIGRATION_DATABASE_URL`); (c) a CLI flag.
B3. Refusal rules: which of these should stop a restore? (i) file isn't a valid backup / row counts don't match; (ii) target has any rows; (iii) target schema/migrations differ from the backup's; (iv) remote (non-localhost) target without an explicit flag; (v) a real run without a prior dry-run. How should (v) be enforced, if at all?
B4. Runtime state on restore: what happens to inbox rows still pending/processing, open pending_actions (unconfirmed cards), chat_lease, job_runs?
B5. How are write_ledger and idempotency preserved (ids, sequences, ledger rows)?
B6. What does "reuses the import path" (SPEC §8 item 9) mean in practice? (a) the same script shape: review → dry-run (transaction + rollback) → real run, one transaction, refusals; (b) convert the backup into the old tool's export format and run `history:import`; (c) restore only `source = import` style rows via import_row_key semantics.
B7. Should restore be possible from Telegram (upload the file to the bot), or local script only?

### C. Cost guard
C1. Should cache tokens count toward the caps, and how? (a) no; (b) all token types at weight 1; (c) weighted roughly by price (cache read ≈ 0.1× input, cache write ≈ 1.25×); (d) switch caps to an estimated money amount with a price table.
C2. Vision: share the AI token cap, or a separate daily cap (e.g. photos per day)?
C3. What should the user see when a cap is hit?
C4. Should there be a `/usage` command (or usage in another message)?
C5. How to fix fact 4 (rows that can't finish within maxDuration)? (a) leave; (b) per-input-kind time budget before claiming a row; (c) shorter timeouts; (d) lower the 45 s stop point for everything.
C6. Keep loop limits (6 turns, 40 s) or change them?

### D. Tool-failure messages
D1. Granularity: (a) one message per failing service (Anthropic, STT provider, Telegram download, DB) with the cause type (timeout, overloaded, rate limit, key rejected, network); (b) one message per service, no cause; (c) a generic message plus the step name.
D2. For errors that go to inbox retries (most often DB): message the user (a) only at final failure, with a reason; (b) on the first failure ("retrying") and at final failure; (c) every attempt.
D3. Should messages tell the user to check configuration (e.g. "API key rejected, check Vercel env") given the user is also the operator?
D4. Where should classification live and what may it read from errors (message text, names, codes, status)?

### E. Known minor issues (docs/STATUS.md) — fix or leave, for each
E1. Duplicate-user-message check in conversation.ts keyed on text, not update id (no migration for it).
E2. A re-import restoring a bot-logged slot that the export no longer has leaves it `source = bot`.
E3. A crash after STT or vision succeeds but before the card is stored re-bills STT/vision on the inbox retry (no duplicate write).
E4. After a re-import, undo of an earlier bot log restores the status recorded at log time.
E5. If marking a scheduled job done fails after its message was sent, the job can send again 5 minutes later while its window is open.
E6. A photo over 3.5 MB gets the generic "couldn't read that photo" reply instead of a "too large" message.

## Answers (independent review)

A1: (c) every public table, with an explicit exclusion list of `inbox` and `chat_lease` only — both are transient queue/lock state (inbox is also the biggest table: raw payloads, `TODO(M9): retention` in schema/runtime.ts), while write_ledger, pending_actions, job_runs, usage_logs and conversation_messages are needed for idempotency, cap continuity and memory context after a restore; a table M7 adds is then backed up by default (the safe direction).
A2: (b) the database catalog (`pg_catalog`/`information_schema`, schema `public`, base tables), also used for primary keys (stable row order), serial sequences and FK order — it covers M7 tables with zero code changes and sees what is actually in the DB, not what the TS exports claim; Drizzle exports are used only in the coverage test (A8).
A3: (a) Postgres-side JSON: per table, sequentially (session pooler, one query at a time), `select coalesce(jsonb_agg(to_jsonb(t) order by <pk>), '[]')`, restore with `insert … select * from jsonb_populate_recordset(null::<table>, $1)` — enums, text[], timestamptz, numeric and jsonb round-trip natively; keep each table's JSON opaque in JS (no parse/re-stringify of values) so numeric/bigint precision can't be lost.
A4: (a) one CSV per table inside a single zip, generated generically from the same rows (jsonb/arrays as JSON text in the cell) — SPEC §5.7 asks for "JSON + CSV of all data"; one zip = two Telegram documents per backup (JSON for restore, zip for spreadsheets) instead of ~25 separate files.
A5: (b)+(c): gzip the JSON once it passes a threshold (e.g. 10 MB) and refuse above ~45 MB with a message giving the size and pointing to a local `pnpm backup` script (same builder, writes to disk, no limit) — single-user data is far below 50 MB today, but conversation_messages/usage_logs grow without bound, so the failure must be explicit, not a Telegram 413.
A6: window Sun 18:00–23:00 Rome (calendar date, like class_question); a failure leaves the row `claimed` and the existing runner retries it every tick (5-min reclaim, SPEC §2); the job sends one failure notice with the classified reason ("Weekly backup failed (database timeout). Use /export or pnpm backup.") only on its last chance (tick at or after 22:30), so transient errors stay silent and a real miss is never silent.
A7: (c) row counts per table plus the week's AI tokens and voice minutes vs caps, all computed in code — the 3–5 line weekly summary (SPEC §5.6e) is a separate Sunday job, so a summary/LLM failure can never block the backup; keep it out of M9.
A8: db-project test on migrated `gymbot_test`: (1) catalog tables == Drizzle `getTableConfig` table names (catches a table missing from either side); (2) every catalog table is in the backup or in the exclusion list, and every exclusion name exists; (3) round trip: fixture rows covering every column type (enum, text[], jsonb, timestamptz, numeric, bigint, nulls) → backup → restore into a truncated DB → per-table `to_jsonb` equality and each sequence's next value > max(id).
B1: (a) only a fresh, empty, migrated database (local or a new Supabase project) — restore is disaster recovery; merging or replacing in place would rewrite history (CLAUDE.md "History is never rewritten") and clash with ids the ledger references.
B2: (b) dedicated `RESTORE_DATABASE_URL`, no fallback (mirrors `MIGRATION_DATABASE_URL`, src/config/env.ts) — `.env.local` holds the production `DATABASE_URL`, so falling back would aim restore at production by default; print host + db name in the review output.
B3: refuse on (i) invalid file / manifest version / per-table counts or sha256 mismatch, (ii) any row in any public table, (iii) migration list differs (backup records the `drizzle.__drizzle_migrations` hashes; restore into the same schema, then `pnpm db:migrate`), (iv) non-localhost target without `--allow-remote`; (v) not enforced in code — empty target + one transaction make a bad real run harmless, and the runbook (docs/STATUS.md "How we work") already requires dry-run first and the user's OK for production writes.
B4: inbox and chat_lease start empty (excluded; `acquireOrRenew` inserts the lease row); pending_actions and job_runs are restored verbatim — open cards are already past `expires_at` (30 min) so existing expiry logic treats them as expired, and `done` job_runs stop a same-day re-send; no special-case rewrite of runtime rows.
B5: insert with the original ids, restore write_ledger verbatim (its `result` jsonb references log group ids), in FK topological order from the catalog (Drizzle FKs are not DEFERRABLE), then `setval` every serial/bigserial sequence to max(id) — without that, a new pending_actions id reuses a restored `p:<id>` ledger key and ✅ silently writes nothing; then run `refreshUserState` since user_state is only a cache (SPEC §6).
B6: (a) same shape as `pnpm history:import` (scripts/history-import.ts, src/db/import-history.ts): read + validate → review summary → `--dry-run` (full transaction, then the DryRunRollback pattern) → real run in one transaction, with typed refusal errors; (b) loses per-set reps/RIR/clean that the old format never had, (c) restores only a fraction of the data.
B7: local script only — the target is a new DB the deployed bot isn't connected to, restore needs a new connection string and can exceed maxDuration 90 s; a Telegram restore would also be a remote "wipe-and-write" command reachable by anyone holding the bot token.
C1: (c) weighted, input-equivalent: `input + output + 1.25 × cache_write + 0.1 × cache_read`, weights as constants in src/ai/constants.ts, summed in SQL in usage.ts — today cached prompt tokens are invisible to the cap; weight 1 for cache reads would burn the 200k daily cap ~10× too fast; a money/price table goes stale when `ANTHROPIC_MODEL` changes.
C2: share the AI token cap — vision is the same Anthropic account and already records into usage_logs (logging-flow.ts `photo`); photos are rare (Thursday board), so a separate per-photo cap adds config without protecting anything.
C3: say which cap and when it resets, numbers formatted in code: "AI daily budget reached (200,000 tokens). Resets at midnight (Rome). Commands still work." / monthly → "Resets on 1 Nov." / voice → "Voice budget reached (30 of 30 min today) …" — the caps are per Rome calendar date (usage.ts), not the 03:00 training-day boundary, so the text must say midnight.
C4: yes, a `/usage` command (code only, no AI, so it works when the AI budget is reached; register in setMyCommands and HELP_TEXT) showing today / this month tokens and today's voice minutes against the caps; the same numbers go in the Sunday message (A7).
C5: (b)+(c): pass the invocation's hard end (start + 85 s) into the handler and clamp the AI loop budget and STT/vision/download timeouts to the time left; before claiming, require a per-kind minimum time left (text/callback ~45 s, photo ~60 s, voice ~75 s) and otherwise stop with "deadline" (attempts untouched) — a row killed at 90 s burns an attempt, waits the 150 s lease and re-bills STT/vision (E3).
C6: keep 6 turns and 40 s as ceilings (SPEC §3 "cap the Claude tool loop"), but derive the effective budget as min(40 s, time left − send margin) per C5; the loop's AbortController already bounds the SDK's 35 s × maxRetries 2.
D1: (a) one message per service (Anthropic, speech-to-text, Telegram file download, database) with a small fixed cause set that maps to what the user should do: temporary (timeout / overloaded / rate limit / network → try again), config (key rejected / quota → check config), input (too large / unsupported), unknown — more causes than that is noise.
D2: (b) first failure → "Database error, I'll retry automatically. Don't resend." and final failure with the reason — retries wait for the next webhook or tick (up to 15 min, process-chat.ts `retry_later`), and a resend has a new update_id, so the write_ledger can't dedupe it and the log is saved twice.
D3: yes, one short hint naming the env var to check ("Anthropic rejected the API key: check ANTHROPIC_API_KEY in Vercel"), never a value — the single user is also the operator (SPEC §1), and SPEC §4 keeps secrets in Vercel env only.
D4: one pure, unit-tested classifier module; call sites wrap errors with the service/step (don't guess the service from the error); it reads only class (`instanceof` SDK/grammY/postgres errors), `name`, HTTP `status`, Postgres SQLSTATE / Node `code`, after unwrapping `BotError.error` and `DrizzleQueryError.cause` — never message text (it carries SQL params and the user's words, process-chat.ts `describeError`); store `service:cause` in inbox.error.
E1: leave — it only skips a repeated identical user line from the 10-message context within 10 min; writes are still deduped by write_ledger, and the fix needs a migration.
E2: leave, document — re-import is a one-off cutover tool (SPEC §8 "Transition"), and after cutover the bot row is the newer truth anyway.
E3: leave — bounded by 3 attempts and the caps, and C5 removes the main cause (kills at maxDuration); a real fix needs a transcript cache keyed on update_id (new table).
E4: leave — only after a re-import, which is a one-off; undo restoring the logged-time status is consistent with "history is never rewritten".
E5: leave — SPEC §2 chose claim → send → done (at least once), the window bounds repeats, and a duplicate backup document is harmless; at most retry `markDone` once in the runner.
E6: fix — before downloading, pick the largest `PhotoSize` with `file_size` ≤ 3.5 MB (Telegram always sends smaller sizes too), and only if none fits reply with a specific "photo too large" message (same D1 "input" cause).

## Other risks
- Sequence reset after restore (B5) is the one bug that turns into silent data loss (✅ hits an old `p:<id>` ledger row); it needs its own db test.
- The tick runs jobs before the inbox sweeper with the sweeper deadline measured from tick start (api/cron/tick.ts): a slow Sunday backup (25+ sequential queries + 2 uploads) eats inbox time; run it after the sweep or give it its own time budget.
- M8 will add `sendPhoto` to JobContext in parallel; agree now on one additive shape (e.g. `send(m)` + `sendFile({ kind: "document" | "photo", name, bytes, caption })`) to avoid a merge conflict in runner.ts and telegram-runtime.ts `sendToOwner`.
- `inbox` retention (`TODO(M9)` in src/db/schema/runtime.ts) isn't in the questions; purge `done`/`failed` rows older than N days in the tick, keeping update_id dedupe for at least Telegram's 24 h redelivery window.
- The backup contains conversation text and memory and goes through Telegram (not end-to-end encrypted): acceptable for a single user, but never log row contents or file URLs in Vercel logs.
